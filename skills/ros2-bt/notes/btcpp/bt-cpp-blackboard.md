# Blackboard, ports and SetBlackboard (with SequenceStar)

**TL;DR** The **blackboard** is the tree's memory: a map of **entries** (key → value). An **output port** writes an entry, an **input port** reads one; in the XML a port refers to an entry with braces, `goal="{Interface}"`. Ports work like function arguments and return values, and one node's output can be another node's input. Port names may differ between nodes; the **key** must be the same. `SetBlackboard` writes an entry from the XML.

## SequenceStar (with memory)
The examples use a `SequenceStar`: once a child returns SUCCESS its status is remembered; if a later child fails, the next tick starts from that child. Children A, B, C, D: A and B succeed, C fails → the next tick starts at C ([[bt-sequence-variants]]). [v4: `SequenceWithMemory`]

## Value created at runtime by a node
```text
[→*] SequenceStar
├── Check robot
├── Calculate goal    Goal Generator → output port  goal = {Interface}  ──▶ writes entry "Interface" = 9;10
└── Robot target      input port  input = {Interface}  ◀── reads entry "Interface" → Read Goal (9;10)

Blackboard:  key "Interface" · value 9;10
```
- Values between nodes flow through the blackboard; here 9;10 is generated by `Calculate goal`.
- The entry does not exist before the program starts: the output port creates it.

## Values defined before the program starts
```text
[→*] SequenceStar
├── Check robot
├── Calculate goal    Goal Generator → output port  goal = {Goal 2}  ──▶ writes entry "Goal 2" = 1;1
└── Robot target      input port  input = {Goal 2}  ◀── reads entry "Goal 2" → Read Goal (1;1)

Blackboard (defined before the start):
  Goal 1 → 9;10     Goal 2 → 1;1     Goal 3 → 5;5
```
The same entries written in the XML:
```xml
<SetBlackboard output_key="Goal 1" value="-1;3"/>
<SetBlackboard output_key="Goal 2" value="1;1"/>
<SetBlackboard output_key="Goal 3" value="10;9"/>
```
(The course's table and XML disagree for Goal 1 and Goal 3; only Goal 2 = 1;1 is used. The table also gives type `double` for these entries, but each value is an x;y pair.)

A value written in the XML is fixed text: it cannot change at runtime unless a node overwrites the entry.

## Strings to custom types (`bt_u3_ex3`)
```text
Robot is OK!
Target positions: [ 1.1, 2.3 ]
Converting string: "5.2;8"
Converting string: "29;9"
Target positions: [ 5.2, 8.0 ]
Target positions: [ 29.0, 9.0 ]
```
- `Robot is OK!`: the robot check succeeds.
- `[ 1.1, 2.3 ]`: the goal calculated by a node, passed as a typed value (no conversion).
- `"5.2;8"`, `"29;9"`: goals stored as text in the blackboard; reading them through a typed input port calls the type's `convertFromString` specialization (it prints `Converting string`), which splits at `;`. The pattern is BehaviorTree.CPP's [tutorial 03](https://github.com/BehaviorTree/BehaviorTree.CPP/blob/v3.8/docs/tutorial_03_generic_ports.md) (`Position2D`).

## Pitfalls
- `goal="{Interface}"` reads or writes the entry `Interface`; `goal="Interface"` (no braces) passes the literal text "Interface".
- Each tree and SubTree has its own blackboard: connect them explicitly ([[bt-cpp-port-remapping]]).
- Ports and the blackboard are for data that changes at runtime; constant setup values go to the constructor ([[bt-cpp-constructor-args]]).
